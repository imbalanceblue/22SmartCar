# M5-2 架构:双轨通信 + 为什么不在比赛时传图

## 1. 一句话架构

小车端**只做聚合与降频**，主机端**只做看、调、记**。
网络上传的是**算好的摘要**，不是原始数据流。

```
小车端(单进程)                      主机端
┌──────────────────────┐            ┌────────────────────────┐
│ dashboard_aggregator │  10Hz 指标  │ app.py                 │
│  ├ 订阅 N 个话题      │ ──────────▶ │  ├ ThreadingHTTPServer │
│  ├ 滑窗算 freq/loss  │  /dashboard │  ├ SSE 推送(EventSource)│
│  ├ 本地判 4 类故障    │   /metrics  │  ├ 状态机镜像渲染        │
│  └ 只发字典          │   /faults   │  └ 一键导出 HTML 快照    │
└──────────────────────┘            └────────────────────────┘
        ▲ 原始话题留在车上                   ▲ 浏览器单向接收
```

**关键分界线**：频率、丢包率、置信度均值都在**小车端**算完才发。
主机端拿到的已经是 `{"freq": 9.8, "loss": 0.02, ...}`，不是时间戳序列。

## 2. 为什么频率/丢包必须在小车端算

如果主机端算，小车必须把**每条消息的时间戳**推上去：

| 方案 | 上行数据量(20 话题 @ 10Hz) | 依赖 |
| :-- | :-- | :-- |
| 主机端算 | 200 条/s × 约 40B ≈ **8 KB/s**，且随话题数线性增长 | 需要独立时钟对齐、需要缓存窗口 |
| 小车端算(本实现) | 10 次/s × 约 400B ≈ **4 KB/s**，与话题数无关 | 无 |

表面上 8 KB/s 也不大，但真正的代价不是带宽，是**时钟**：
时间戳来自小车，主机要算频率就得维护"每个话题的到达窗口"，
一旦网络抖动，主机看到的间隔会被拉长，算出来的频率是**网络的频率**，不是**传感器的频率**。
传感器降级这件事，只有在小车端观察才准。

## 3. 为什么 `/dashboard/metrics` 定 10Hz

三个约束的交集：

1. **人眼**：折线图超过 10Hz 的刷新人眼分辨不出，只会增加渲染开销；
2. **带宽**：10Hz × 400B ≈ 4 KB/s，USB 网卡、Wi-Fi、手机热点都能稳定承载；
3. **降频比**：原始 20 话题 @ 10Hz = 200 条/s，聚合成 10 条/s，**降频 20 倍**。

如果改成 1Hz，急停、撞墙这类事件在图表上会"跳变"而不见过程；
如果改成 50Hz，带宽涨 5 倍，而人眼得不到任何额外信息。

## 4. 为什么高频指标走 DDS 而不是 WebSocket

| 维度 | DDS(原生) | WebSocket(JSON) |
| :-- | :-- | :-- |
| 序列化 | 二进制，零拷贝 | JSON 文本，编解码有开销 |
| 延迟 | 同机 < 1ms | 同机 1~5ms，跨网再多一跳 |
| 依赖 | 已在 ROS2 里 | 需要 rosbridge 或自建 WS 服务 |

但**本题实现并不真的跑 ROS**（纯软件、可在无 ROS 环境演示），
所以代码里用一个 10Hz 主循环**模拟** DDS 的高频轨，
浏览器侧用 **SSE**（Server-Sent Events）做单向推送 —— 与 WebSocket 相比：

- 仪表盘是**纯下行**场景，SSE 够用，浏览器原生 `EventSource` 零依赖；
- 不需要握手升级、不需要心跳包，断线由浏览器**自动重连**；
- 上行操作（急停、复位）走普通 `POST`，频率极低，不需要长连接。

**如实披露**：若现场要求真接 ROS2，把主循环换成 `rclpy` 订阅、
把 SSE 换成 `rosbridge` 的 WS 即可，界面与聚合逻辑不用改。

## 5. 为什么比赛默认不传图像

题面原文："网络传状态与指令，不传图与云。"

一张 320×240 的 MJPEG 帧约 **15~25 KB**，1Hz 就是 20 KB/s，
是全部指标数据的 **5 倍**，而它提供的信息（"看到什么了"）在比赛判罚中
几乎不用 —— 判罚依据是**状态、时间、指标**，不是画面。

实现上做成**参数而非约定**：`config/dashboard.yaml` 的 `video.enable: false`，
默认关闭，现场改 `true` 才开，且限 1Hz / 320×240。考官查的就是这一项。

## 6. 20 个原始话题要开多少订阅

**20 个**。聚合节点按 `topic_patterns` 展开匹配到的每个话题各开一个订阅，
每个订阅的回调只做一件极轻的事：`TopicStat.on_msg()` 里 append 一个
`(recv_time, stamp)` 二元组，**不做任何计算**。

计算集中在 10Hz 主循环里做一次滑窗统计，所以：

- 订阅回调的耗时是 **O(1)**，与话题数量无关；
- 20 个订阅带来的开销主要是回调调度，实测 CPU 远低于 0.5%；
- 真正的风险不是"订阅多"，而是**回调里做重活**——本实现刻意避开。

## 7. 断线与"没数据"的区分

`TopicStat` 里有一个 `recv_count`：**累计收到过多少条**。

- `recv_count == 0` → 从未收到，面板显示 `—`（未知），不画成 0；
- `recv_count > 0` 且当前窗口为空 → 曾经有过，现在断了，显示"失联"并触发掉线故障。

这条是为了避免题面点名的典型翻车：**把"没收到数据"画成 0**，
看起来像指标突然掉到零，而实际是链路断了。
