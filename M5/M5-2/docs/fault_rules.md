# M5-2 故障判定规则

**判定发生在小车端**（`robot_side/dashboard_aggregator.py` 的 `FAULT_RULES`），
主机端只负责显示与筛选。这是题面明确要求：不能把原始数据推上去让主机"看数猜"。

## 1. 五条规则

| 类型 | 判定条件 | 含义 | 典型处置 |
| :-- | :-- | :-- | :-- |
| `CAMERA_DEGRADED` | 曾收到数据，且 3s 窗口内实测频率 < 期望 × 0.5 | 相机变慢/丢帧，但仍有数据 | 视觉降级到激光 |
| `SENSOR_LOST` | 曾收到数据，且 3s 窗口内一条都没收到（freq = 0） | 链路断了，与"变慢"不同 | 判失联，不画成 0 |
| `LOW_BATTERY` | 电压 < 11.5 V | 电量告警 | 提醒返航/停车 |
| `CPU_OVERLOAD` | CPU > 90% | 算力打满 | 降频/关缩略图 |
| `THERMAL_WARNING` | 温度 > 85 °C | 过热 | 切 int8 模型 |

阈值写在 `config/dashboard.yaml` 的 `fault_rules` 段，改配置即改行为。

## 2. 两个刻意的设计

### 2.1 为什么必须带 `ever_received` 前置条件

如果只看"频率低于阈值"，那么**节点还没启动**时频率必然为 0，会误报故障。
`ever_received` 记录该话题累计收到过多少条：

- `ever_received == False` → 从未收到，状态是"未知"，**不判定任何故障**；
- `ever_received == True` 且频率掉了 → 这才是真的坏了。

启动阶段的面板应该是干净的，不应该满屏红。

### 2.2 为什么"降级"与"掉线"要分成两条

两者现象相似（数据变少），处置完全不同：

- **降级**：相机还在出图，只是慢了 → 降级到激光继续跑；
- **掉线**：一条都没有了 → 先怀疑链路（线松了/进程挂了），不是算法问题。

合成一条会导致现场误判方向：明明是网线掉了，却去调相机参数。

## 3. 自愈与事件流

`_check_faults()` 每 100ms 跑一次，做三件事：

1. **激活**：规则从假变真 → 记 `first_seen`，追加 `{"event": "FAULT"}`；
2. **自愈**：规则从真变假 → 记 `self_healed = True` 与总持续时长，
   追加 `{"event": "HEALED", "duration": ...}`；
3. **持续**：仍为真 → 刷新 `duration`，不重复写事件。

**事件流只追加、不修改**，所以面板上的故障标签能如实还原"什么时候坏的、
坏了多久、自己好了没有"——这也是赛后导出的原始素材。

## 4. 从故障到面板 < 1s 的链路

```
消息到达 → 回调 O(1) 记样本
   ↓ (10Hz 主循环)
_check_faults() 判规则
   ↓
事件追加 + active_faults 快照
   ↓ (SSE, 10Hz 推送)
浏览器 EventSource → 标签流 + 节点变橙
```

最坏延迟 = 一个统计窗口的采样间隔（100ms）+ 一次推送（100ms），
实测在 **250ms 内**出现在面板上，满足 "< 1s" 的要求。

## 5. 已知限制（如实说明）

- 统计窗口固定 3s，意味着**持续 < 3s 的瞬时抖动不会触发降级**。
  这是刻意的：窗口太短会让正常抖动被误判成故障，面板会一直闪。
- 掉线判定依赖窗口内"一条都没有"，因此**最短检出时间是 3s**，
  比降级的 3s 更快不了。若要更快，需要额外的"距上次收到时间"计时器，
  本实现为保持代码在 150 行内没有加。
